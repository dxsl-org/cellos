#### [S-1] Published GitHub Release kernel is built with the public dev trust anchors (dev-policy-key, dev-signing-key, dev-weak-rng) — Severity: High — STRIDE: S/E — OWASP: A02/A08
- Where: .github/workflows/release.yml:38-47; kernel/Cargo.toml:68-82, 97-99; scripts/sign-policy.py:57; scripts/sign-cell.py:63; docs/security-model.md:246-250
- What: `release.yml` runs `cargo build --release --target riscv64gc-unknown-none-elf` with default features and uploads the result as the GitHub Release artifact. `kernel/Cargo.toml` `default = ["dev-policy-key","dev-signing-key","dev-weak-rng","signing-required","native-domains"]`, whose trust anchors are the hard-coded seeds `0x42*32` (policy) and `0x43*32` (cell signing) committed in scripts. The documented release posture (`--no-default-features --features release-posture`, security-model.md:247-250) is never used in any workflow; `release-signing-key`/`CELLOS_RELEASE_CELL_PUBLIC_KEY` are not referenced by any workflow or script (grep over .github/scripts). `dev-weak-rng` also makes `GetRandom` fall back to xorshift32.
- Exploit: Anyone can mint a valid `__ViCell_sig` and a valid signed `/POLICY.BIN` for a device running the released kernel using the repo's seeds (`scripts/sign-cell.py --unchecked-dev-signature`, `scripts/sign-policy.py`), granting arbitrary capabilities to an attacker cell; TLS/broker RNG in such an image is predictable.

#### [S-2] Default TLS trust anchor `private.der` has its CA private key committed (`tools/hypha-mock-llm/ca-key.pem`); production checker accepts it — Severity: High — STRIDE: S/I — OWASP: A02/A07
- Where: cells/services/net/Cargo.toml:19, 47; cells/services/net/src/tls/roots.rs:70-71; tools/hypha-mock-llm/gen-dev-ca.py:4-16, 44-46; tools/hypha-mock-llm/.gitignore:4; cells/services/net/roots/README.md:10, 14-17; scripts/check-production-relay-image.py:22, 30-35, 80-83; scripts/test_check_production_relay_image.py:27
- What: `service-net` default features embed `roots/private.der` as the sole TLS root. That DER is generated by `gen-dev-ca.py` from `ca-key.pem`, which is intentionally tracked. `check-production-relay-image.py` treats `tls-ca-private` as one of the four acceptable production CA features and does not verify that the embedded root differs from the committed dev CA, so a "production" image passes the gate while trusting a public key pair.
- Exploit: A network peer on path holding `ca-key.pem` issues a leaf cert for any hostname; every verified-TLS connection from a default or relay image (KMS, LLM gateway, https-demo) accepts it → full MITM of fleet TLS.
- Fix: Untrack `ca-key.pem` (rotate the CA); make `check-production-relay-image.py` reject an image whose embedded root SHA-256 equals the dev `private.der`; make `tls-ca-private` non-default or require `CELLOS_FLEET_CA_DER` at build time.
