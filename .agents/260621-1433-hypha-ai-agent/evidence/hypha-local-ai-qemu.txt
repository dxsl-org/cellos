Launch-edge finding (reproduced, then fixed)
--------------------------------------------
First gate run, before the VIFS1 staging:

  [loader] DENY launch edge: caller=18 name=shell route=Elf target=/bin/hypha
           spawn_cap=false supervisor_cap=false
  shell: command not found: hypha

The reviewed `(shell, Path, /bin/hypha)` edge exists and carries `spawn`, but the shell's VFS+grant
spawn attempts the ELF route first, and `launch_profile::authorize` refuses any capability-bearing
ELF route ("caller-owned bytes must not borrow authority"). The documented fallback is the raw
`SpawnFromPath` route, which resolves through the kernel loader: VIFS1 first, then the block table.
`EarlyLoader::probe()` however runs before any block driver exists on RV64 and is never retried, so
the block table stays unprobed and VIFS1 is the only source that answers. `/bin/hypha` was in
neither — every route failed. `/bin/tool-spawn` is the same case on Hypha's own child edge (its
reviewed ceiling is `{spawn}`), and `gen_disk.ps1` now stages both into VIFS1, the same class as
`/bin/bench`.

Root cause of the now-common `DENY ... route=Elf target=/bin/hypha` line in a passing run: the shell
tries the ELF route first and falls back; the denial and the successful path spawn are one event.

Harness note
------------
One harness serial write of `exit` was observed to vanish (no kernel echo of the keystrokes) while
the same input typed over QEMU's stdio console is read normally, so the gate retries that line once.
Serial write errors are swallowed by the harness, which is why the log cannot distinguish a dropped
write from an ignored command.

Ceiling: QEMU software integration only. The resident model is the deterministic fixture, whose
output is not language — this evidence covers wiring, not text quality, latency, throughput, board,
accelerator, or production qualification.
