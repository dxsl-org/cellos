**The six ceilings of K4b CP1 section 0 apply to every RT1 status report and to the dossier** (`reports/k4b-cp2-dossier.md` section 0 requires it, and this text carries them): (1) **no rollback protection** - an older consistent pair, or both files deleted, loads silently; the A/B chain is a forgeable tripwire; (2) **no crash or power-loss durability claim** - "persisted" = `VfsRequest::Write` Ok and an immediate same-boot byte-equal read-back; a torn tombstone resurrects a key; (3) **the dev root MAC key is a public constant co-resident with the data** - a format check, not authentication; (4) **confidentiality at rest is the passphrase and the bcrypt rounds only** (the RT1 key is a TEST key); `Plain` is never written; (5) **the failure counter, unlock slot, import slot and replay floors are volatile**; (6) **the volume is the shared `/srv` CellosFS**: a write failure poisons the backend for every user until reboot. Label `DEV_POSTURE`, never `ProductionQualified`.

## 7. Boot-role channel, orchestration and quiescence

### 7.1 Why a channel is needed and what was examined

A second boot of the same ISO must know it is boot N, and the host must be able to **verify** that. Examined (all against the landed lane): the ISO-embedded `kssh.conf` is identical for every boot of one ISO (the kernel embeds `kernel_fs.img` via `EMBEDDED_OVERRIDE`, so a per-role file means a kernel rebuild per role); P1 holds only the three config files and `mkfat32_inplace.py` can only seed those (a marker file needs a tool edit or an unverified mtools write; `phase09_trust_disk.py:6-9`); a guest-written marker on P1/P5 would be reverted together with the disk in boot 5 (the role would follow the rolled-back state) and a failed persistence would be hidden by an adaptive driver; kernel `kill` and the shell's `shutdown` are refused. The Docker fixture, by contrast, is host-controlled, outside the guest disk, already the guest's S00 peer and already driven by `docker exec` in the lane (ledger collection).

### 7.2 The channel (D-RT1-1 option A, recommended)

Before boot N the runner executes `docker exec CONTAINER sh -c 'printf "role=%s\n" N > /tmp/kssh-role'` (root writes a world-readable file; the user `tester` reads it; no secret). The driver's S00 in every boot runs `ssh --user tester --auth password -p PORT 10.0.2.2 --command 'cat /tmp/kssh-role; echo kssh-s00'` (today's S00 is `login(a, &f, "10.0.2.2 --command 'echo kssh-s00'", password)` with the fixture password, `kssh.rs:617-637`; the T1 variant only lengthens the remote command, a line of about 95 bytes for a five-digit port, within the shell's 128-byte line [INFERENCE: length not measured] and expects stdout `role=N` then `kssh-s00`) and parses `role=N` from stdout, prints `P04 INFO kssh-obs role n=N` and `P04 PASS|FAIL kssh-role`, and runs the scenario list of role N. The host judge compares N with the boot index it launched (**mismatch or missing = class E**: a channel failure is a host failure, not a product result). The role carries **no authority**: it only picks which scenario list runs; every pass criterion is judged on the host from sources the guest cannot choose (sshd log, ledger, disk records, serial). The channel is exercised by the password login that every boot needs anyway (an S00 failure ends the boot: no role, no scenarios, class C/E). The same ISO hash, the same QEMU argv (except the disk path and the socket path) and the same fixture container are verified across boots (`argv-equal-modulo-disk`).

### 7.3 Orchestration (`scripts/kssh_boots.py`; the runner builds everything, then hands over)

Inputs from the runner: the ISO, the disk `D0`, the container name, the evidence directory, the key directory. For N = 1..5:

1. write the role (7.2); record the pre-boot `docker logs` line count and the ledger line count;
2. start QEMU with the T0 argv (`-machine q35 -accel tcg -cpu qemu64,+pdpe1gb,+rdrand,+rdseed -m 256M -display none`, serial chardev socket, `-cdrom ISO -boot d -no-reboot`, one `-netdev user,id=net0` + e1000, the NVMe drive on the boot's disk file), the same asserts (one user netdev, no forwards, no `restrict`), `qemu-argv.txt` per boot; pump the serial socket until `P04-TERMINAL:` or the **1,800 s** window;
3. on the verdict line wait 3 s, `SIGTERM` QEMU, wait up to 10 s; escalation to `SIGKILL`, or a QEMU still alive, marks the boot **unclean = class E** and **no snapshot is taken from it**;
4. wait for QEMU's exit (`proc.wait()`), then the **settle rule**: poll `docker logs` until the line count is unchanged for 3 s (at most 30 s); the lines since step 1 are boot N's `sshd.log` slice (a connection cut by the QEMU exit logs its close after the exit; the settle rule keeps it in the right slice; an orphan close line in the next slice is class C); the ledger slice likewise;
5. only now touch the disk: save serial (`serial.raw.log`, `serial.log`), run `kssh_records.py` on the disk (section 9) and the canary scan of the whole disk file, record its SHA-256;
6. after boot 1: **S1** = `cp --sparse=always D0 S1` (SHA-256 recorded; S1 is never booted and never written); before boot 5: **S1r** = `cp --sparse=always S1 S1r`; boot 5 runs on S1r;
7. apply the gate rules (12.5): continue, or STOP the sequence.

A "clean shutdown" in this lane therefore means: the driver completed its scenario list (every KMS write was acknowledged in the guest), the host ended QEMU by `SIGTERM`, QEMU exited by itself, and the guest's NVMe writes are in the host file [INFERENCE: QEMU's raw file backend with the default cache mode writes through the host page cache and closes the backend at `SIGTERM`; B0 reads the records back to confirm]. It is **not** a guest-initiated flush or power-off and proves nothing about power loss.

## 9. Secret scan of the disk at rest and the record oracle (host side, after every boot)

**Images scanned:** `D0` before boot 1 (a baseline: no canary, no record) and the live disk after each of boots 1-4 and `S1r` after boot 5 (six scans), plus `S1`'s SHA-256 before and after boot 5 (must be equal: the pristine copy was never touched). The ISO is excluded as in T0 (it carries the passphrases and key files by design).

**Secrets (must be absent from every image):** PASS_A and every WRONG value; the 32-byte seed and the 64-byte expanded private section of `ka16` and `kp0` (the decrypted inner section contains `seed || pub`, so the 64-byte form detects it); the `kp0` armor text, base64 body and container magic; the **`ka16` container text** (armor lines, base64 body, `openssh-key-v1\0` magic: the persister stores only name, public key, rounds, salt and ciphertext, never the container); the malformed variants' text; the lane signing seed, the fixture host private key and password; forms as `k8-cp1.md` section 9 (raw, hex, base64 std/url at the three alignments, decimal lists; strings < 8 bytes are not used). **Not secrets** and expected: the public key and fingerprint, the verbatim **wrapped ciphertext** (it *is* on disk by design: the positive control), the dev-root label `CELLOS-KSSH-T1-DEV-ROOT-v1` and the record magic.

**Controls (the scan must not be vacuous):** (1) the existing planted-canary controls before and after the scan, applied **to a copy of a data-bearing region of a real image** (including a plant that straddles a chunk boundary and one at a sector-unaligned offset) so the disk code path, not only the serial one, is proven to detect every form; (2) after boot 1 the host-derived ciphertext of `ka16` **must be found** - attribution of a miss: if boot 2 later loads the key (`kssh-t1-load` passes) the bytes are on disk in a form the finder cannot see (layout, class C, see the caveat below); if boot 2 also fails to load it, persistence failed (class D, K4b); (3) the expected public strings of T0 plus the persist banner are found in the serial. A failed control is class E; a canary hit in a real image is class D (stop-ship for K4b if it is a secret form) unless it is a control artefact, and is final.

**Record oracle (`kssh_records.py`).** The finder searches each image for the 6-byte prefix `CKMS\x02` followed by a valid slot/kind/state, decodes every candidate with the strict K4b decoder (exact length, zero padding, known enums, bounds 144..=2,048 and a multiple of 16, name charset, MAC **checked first** with `blake2s(key=BLAKE2s-256(label))`) and returns the **set of distinct valid records** (CellosFS may leave stale copies of overwritten extents; a set, not a count, is judged). Expected sets are in the table of section 8; per record: **R1** = slot A, present, name `ka16`, custody 2, public key = the host's, rounds 16, salt and ciphertext = the host's values from the container parse, `previous` all zero, revision 1, and the **whole record equals the host's independent encoding** of those fields (exact bytes); **R2** = slot B, tombstone (all value fields zero), `previous` = `BLAKE2s-256(R1 bytes)`, MAC valid (its revision is recorded, expected `R1+1` [INFERENCE from `next_revision()`], not judged). The verdict is on the **valid** set: an extra valid record, a valid record with another slot/name/key, a MAC-valid record that the strict decoder rejects (a format violation by the writer, e.g. custody 1 = Plain), or a valid set that differs from the table is class D with the image and offset named (no secret bytes are printed). Candidates that fail the MAC are **recorded with offset and reason but not judged** (a torn or stale extent left by CellosFS's in-place replace is possible and is not a product claim; [INFERENCE] B0 shows whether any exist). The v2 magic never appears in `slot-*.bin` form (v1 relay records `CKMS\x01`, 186 bytes): none are expected; one is recorded as an observation.

**Layout caveat [INFERENCE].** The finder assumes a record (`<= 2,297` bytes) is stored contiguously in the P5 image as written; CellosFS is a plain engine (`libs/cellos-fs`, CRC32 on metadata) and nothing read says it transforms file data, but no RT or B0 has ever looked. B0 settles it. If B0 shows the bytes are not found, RT1 does **not** run on a guess: the fallback needs a CellosFS-aware reader (not existing; decision D-RT1-6) or the presence/absence evidence reduces to the secret scan alone with the loss of the record oracle stated.

**Serial and logs (every boot):** the T0 targets (serial raw/clean, sshd slice, ledger slice, `qemu-argv.txt`, every judge output, the archive before it is copied into the repository) are scanned with the T1 canary set **plus the leak needles** (ciphertext forms and `CKMS\x02`): the ciphertext and the magic must **not** appear on the serial (a `cat` of the record file that succeeds is class D). The archive allowlist (`ALLOW`/`FORBIDDEN` of the judge) is unchanged: no `*.img`, `*.iso`, keys; the per-boot disk findings are archived as `disk-after-bootN.json` (hash, set of records by slot/state/revision/MAC verdict, scan summary) without bytes.

### 12.5 Classes and STOP rules (modelled on `k8-cp1.md` 11.4; "first sign epoch" = boot 1's `kssh-s02`; "first persistence epoch" = boot 2's `kssh-s02r`)

| Class | Condition | Consequence |
|---|---|---|
| **A SUCCESS_COMPLETE** | all five boots executed in order; every pass criterion met (host oracles included); the six disk scans and the log scans clean with passing controls; the record sets equal the tables; census equal | evidence for T1 at the stated ceiling |
| **B SUCCESS_CORE_ONLY** | boot 1 passes through `kssh-s02` (first sign epoch) **and** boot 2 passes `kssh-t1-load` and `kssh-s02r` (first persistence epoch) with the scans clean up to then, then any later STOP | persistence across reboot proven; every unrun or failed later row listed as unproven |
| **C OBSERVABILITY_INCOMPLETE** | healthy host but an oracle cannot attribute: record bytes not found (layout), sshd slice orphans, wording mismatch, deadline expiry without cause, missing log | recorded as is; no inference of success or of a product failure |
| **D OBSERVED_NEGATIVE_RESULT** | oracle integrity proven and the product contradicts a criterion: a secret form on any disk image or on serial/logs; a Plain key on disk; the key absent after reboot while a valid record is on disk; the deleted key back after boot 4; the key absent on the S1 replay; replay facts differ from boot 2; a locked counter after reboot; any readable record from the shell; `PersistFailed`, `readiness: Unavailable` or a K6/K5 bound violated on healthy hardware; a record set different from the table; a password fallback; a forbidden admission | a real finding, final; **any D on a secrecy or admission row is stop-ship for the owning slice** |
| **E HOST_FAILURE** | QEMU/Docker/serial/harness exception, unclean QEMU exit, role mismatch, scanner control failure, census drift, cleanup failure, wrong banner (custody build booted), unattributed stop | host defect recorded; not a verdict on the product |

Precedence before the first persistence epoch passes: E, then C, then D; afterwards the class is A or B by progress and any later E/C reason is a tail STOP. **Gate rules:** the sequence continues to the next boot unless (a) the QEMU/Docker/harness failed (E) or no driver verdict was produced (C), (b) a *gate row* failed: boot 1 `kssh-s01`/`kssh-s02`, boot 2 `kssh-t1-load`/`kssh-s02r`, boot 3 `kssh-t1-del` (the premise of boots 4-5), boot 5 needs only a clean S1; a non-gate row failing is recorded and the sequence goes on.
