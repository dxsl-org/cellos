Cellos AI inference oracle on physical Raspberry Pi 3 — evidence summary
=======================================================================

Two board runs over the existing static-TFTP netboot lane, both driven from the board's own console
(`ai-test`) with a timestamped transcript captured by `tools/rpi3-netboot/serve-ai-oracle.ps1`.
Board: Raspberry Pi 3 Model B+ (U-Boot reports `RPI 3 Model B (0xa22082)`, `DRAM: 948 MiB`).

What these numbers are
----------------------
- `resident bytes 1220116` for a 1 185 376 B checkpoint is the AI cell's footprint on the board:
  weights + KV cache + scratch, inside the 32 MiB Cell VA slot and the 29 MiB `large-arena`.
- 70 ms to read 1.2 MB through the kernel capability path, against 20+ minutes that never completed
  for 26.7 MB through the VFS IPC path (4000 B per round trip; phase-05).
- 24 tokens in 739 ms is a QEMU-free, TCG-free number on real Cortex-A53 silicon for that checkpoint.

What these numbers are not
--------------------------
No production, security, or fleet claim, and not the 25.6 MiB-checkpoint case: that size is blocked
on this board by two reproduced defects of the board path — a 43.6 MB embedded payload panics the
kernel at compositor setup (phase-04), and a 26.7 MB card-resident checkpoint does not finish loading
(phase-05). Both are reported with their reproductions; neither is a property of the engine.

Also recorded from these runs: the console command is the bare `ai-test` (the shell prefixes `/bin/`
and mangles an explicit path into `/bin//bin/<name>`), and the board's USB/Ethernet driver retries
`[dwc2] TIMEOUT … TX packet transmission failed` continuously once the NIC cell is up.
