Cellos AI inference on physical RPi3 with the 25.6 MiB checkpoint — evidence
===========================================================================

Board: Raspberry Pi 3 Model B+ (U-Boot: `RPI 3 Model B (0xa22082)`, `DRAM: 948 MiB`).
Payload: `cellos-ai-15m-diag.uimg` = the 43.6 MB netboot payload (AI cells + `stories15M-q8_0`,
26 671 328 B, embedded in VIFS1) carrying the image-sized memory-map fix plus temporary boot
diagnostics. Transcript: `rpi3-15m-diag-20260915-073106.log`.

Boot-time memory map after the fix (the same payload panicked before it)

    [boot] kernel_phys_base=0x0000000000080000
    [boot] map base=0x0000000000080000 len=0x0000000002a00000 ty=Kernel     <- 42 MiB, covers the image
    [boot] map base=0x0000000002a80000 ... ty=Usable
    [boot] allocator range 0x0000000002a80000..0x000000003b000000 bytes=0x0000000038580000

Before the fix the same boot printed `len=0x01000000 ty=Kernel` (a fixed 16 MiB) and an allocator
range starting at `0x01080000` — inside a 43.6 MB image — which is why the compositor cell's first
pages overwrote the kernel and every run panicked.

What this is
------------
CP-3's third leg at the `physical` development-hardware ceiling, with the checkpoint the leg is about:
a 25.6 MiB Q8_0 checkpoint resident inside the AI Cell — `resident bytes 28 087 038`, the same number
the QEMU legs predicted — generating coherent prose on real Cortex-A53 silicon at ~6 tokens/s, over
typed IPC, with init supervising the service.

What it is not
--------------
No production, security, or fleet claim. RPi3 remains a development board and never a
production-security qualification target. The ~6 tok/s is this board with this checkpoint, not a
product throughput claim. The fix under test is in the board's fallback memory map; the QEMU legs
(aarch64 virt / riscv64) and their kernels are untouched.
