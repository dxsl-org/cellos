AP-15 vs the canonical init under SMP:
- Arming happens AFTER the real `/bin/platform` spawn (main.rs:1510) and with hart 1 online. Platform's tid, measurement entry, CellSpawn+CellMeasure audit are in `before`. Platform (cells/services/platform/src/main.rs, no `spawn`, "sys_exit(0)" after ECAM scan) may exit inside the window: that only adds CellExit audit and quota/zombie changes, which the contract tolerates (`>=36`, `quota != before`). [V]
- Nothing else spawns between arm and finish, EXCEPT hart 1 can pick up init as soon as `push_ready` publishes it (launch.rs:323) and run it concurrently with hart 0's `finish_trusted_success`. If init's first `Spawn`/session publication (or any thread spawn) reaches `publish_prepared` before hart 0 takes the SCHEDULER lock in `snapshot()` (success.rs:40, scheduler lock first), then `next_task_id == before+1` and `measurements == before+1` both fail ⇒ **boot-fatal panic (assert at cases.rs:227)**. The earlier flakes noted in success.rs:28-37 and 43-54 (queue membership, audit multiple-of-18) already show init being stolen and run inside this window on 2 harts. Init must first read/verify/load a service ELF before its first publish (milliseconds; ed25519 over hundreds of KB), vs microseconds for hart 0's snapshot, so the practical probability is low but non-zero and grows if the hart-0 vCPU thread is descheduled by the host (parallel QEMU runs / CPU storm). [I]
- The canonical init differs from the lane's init in size (1.3 MiB vs ~44 KB) and in being the real launcher: it is the first user code that actually publishes tasks. In the lane the test init is much shorter lived, so this race is untested with the canonical init.
- Everything else in the AP-15 contract is image independent. [V]

## 3. Which checks are likely to FAIL with the canonical image / 2 harts / 2 GiB

Ranked by (boot-fatal) × (plausibility):

1. **AP-15 race on 2 harts** (A15-finish): `next_task_id+1`, `measurements+1` break if canonical init publishes anything before hart 0's `snapshot()`; boot-fatal panic. Low per-boot probability, host-load dependent. [I]
2. **x86 frame-ledger equality with the 9x larger init** (ALIGN/`LEDGER_WARMUP_CYCLES=6`, plus `free_frames` equality in every full-rollback case and `ap02_cleanup_complete`): boot-fatal assert via `assert!`/`assert_eq!(failures,0)` if the identity-map PT ledger doesn't settle or moves in a later case. Never exercised with the canonical init (CI lane uses the 44 KB init). [I] Everything else the corpus needs from the image I checked and it holds (sig OK, `/bin/vfs` present, policy rows for platform and vfs equal to ceilings → expected audit counts 2/2/2/1 hold).
3. `domain_switch_tests::run_primary` on the production profile logs `S22-X86-ADMISSION-ENABLED: FAIL` (admission was never enabled by boot) and then force-enables admission (domain_admission.rs:500). Not fatal; behaviour change only for domain-class cells (M10).
4. `S22-X86-ADMISSION-PUBLICATION-DENY` frame-ledger compare can fail due to hart 1 allocating concurrently (log only).
5. SVM smoke (M14) only if the QEMU CPU model exposes SVM/VMX and boot entered root operation; otherwise SKIP.
6. 2 GiB / 2 harts: no corpus assertion depends on RAM size or hart count except `ready_reservation_contract`, which is skipped (returns true) once the RT hart is online and runs before secondaries here (denials.rs:199-201), and AP-15's window above.

## 4. Persistent observable differences vs a production-feature kernel (for the measurement study)

- **User/kernel stacks of every ELF cell start filled with 0xA5** (S1). Watermarks measured by any other scheme (e.g. zero-prefix scan) will read the whole stack as dirty.
- tids / cell ids / VA slots of real cells are unchanged by the corpus: `next_task_id` is restored or untouched (snapshot-compared / `task_id_selftest` restores it), `reserve_next` is lowest-free, `free_cell_va` restores BUMP. First real task is the platform cell, then init, both as in production. `NEXT_CELL_GENERATION` is ~30-40 higher.
- Pre-init audit ring ≈ +1.5-2 KB; measurement log has ≈68 junk entries and a different aggregate; ADMISSION_REGISTRY populated; Tier-2 admission ENABLED (M10); a few leaked frames (private root from `run_pinned_retire_regression`, x86 identity-map PTs/PD).
- Kernel heap: persistent capacity growth of measurement Vec, scheduler task table, ready queues, CELL_AUTHORITIES, session tables (tens of KB [I]); transients ≤ ~3 MB (ELF reads 613 KB + aligned copies + 1.5 MB reloc vec) inside a 32 MiB heap.
- Serial: ~60 `[ok]` + ~40 `ATOMIC_PUBLICATION_*` + selftest lines (≈150-250 lines) pre-init, plus `[loader] boot-ceiling … narrowed` error lines (~6 cases × ~6 lines), `ELF LOAD` info lines for every prepare in the corpus (~25 prepares × segments), later one-time `[stack-baseline]` warns. Log level itself is Info in both builds (explicit `[logging]`).
- Boot time: ~25 `prepare_elf_task` of the 1.3 MiB-memsz init (page zero/copy + 2×stack priming), ~7 ed25519+sha256 passes over 400-600 KB, O(n²) probe in RF/RM/RW. Seconds in TCG [I].
- Run time: S1 memset per spawn; S7 per-tick scheduler lock + task scan (any hart) after tick 1500.
