This continuation inspected primary upstream manifests, licenses and selected source files over read-only HTTPS on 2026-10-20. The existing host `text-engine` baseline (38 passing tests) belongs to `baseline.md`, not dependency-port evidence.

**Proposed review pins are now concrete:** Ratatui release `ratatui-v0.30.0` at `0a2a7c0363a4806b0cf05c1915bf7cdd438f756c`, using its `ratatui-core =0.1.0` and `ratatui-widgets =0.3.0` packages with defaults off; Kibi reference-only revision `1c33ca09e5a2573a3331faf78f79ac6572969409`; ripgrep `15.1.0` at `af60c2de9d85e7f3d81c78601669468cf02dabab` with the five component versions below; and Sunset core revision `62b98f3996c88cf920cac1653e1c9e15ddf0d7d0` (manifest version `0.6.0`). These are not present in the workspace lockfile. Direct/source pins do not freeze their semver transitive dependencies.

**Source-backed conclusions:** Ratatui has a real `no_std` core/backend interface; its wrapper's disabled defaults do not disable the widgets package's own calendar default. Kibi is a permissively licensed design/adaptation reference, not a portable crate to link. Stock ripgrep components are **not** `no_std`: even `grep-matcher` names `std`, and searcher/ignore require additional OS/runtime surfaces. Sunset is the preferred conditional SSH core because its IO-less synchronous API fits the existing runtime; entropy integration, key decoding, persistent trust and rekey qualification remain real work. Russh is not selected because its mandatory Tokio/std surfaces require a much larger unadmitted runtime. The existing unsafe Cellos SSH server remains excluded.

## Architecture

The workspace is a statically linked Cell system: application/service crates use `ostd` and `api`; builds target bare-metal `core,alloc` profiles and package signed cell images. `text-engine` isolates pure, host-testable text/regex logic from shell-specific `ostd` lang items. The current terminal depends on pixel-oriented `viui`, while the accepted Cellbox design requires a separate reusable terminal SDK and Ratatui backend. Existing `service-sshd` is an inbound, unsafe prototype with isolated crypto primitives—not an appropriate client or controlled interoperability server.

The admissible path remains: retain the exact candidate choices below, obtain only the scoped acquisition/probe/source admissions actually needed, and honor each controlling CP1 before dependent ABI work. Dependency preparation does not release implementation, signing, image, lock or remote gates.

## 2. Ratatui candidate and backend boundary

Primary release sources read: [workspace manifest](https://raw.githubusercontent.com/ratatui/ratatui/ratatui-v0.30.0/Cargo.toml), [facade manifest](https://raw.githubusercontent.com/ratatui/ratatui/ratatui-v0.30.0/ratatui/Cargo.toml), [core manifest](https://raw.githubusercontent.com/ratatui/ratatui/ratatui-v0.30.0/ratatui-core/Cargo.toml), [widgets manifest](https://raw.githubusercontent.com/ratatui/ratatui/ratatui-v0.30.0/ratatui-widgets/Cargo.toml), [core lib](https://raw.githubusercontent.com/ratatui/ratatui/ratatui-v0.30.0/ratatui-core/src/lib.rs), [widgets lib](https://raw.githubusercontent.com/ratatui/ratatui/ratatui-v0.30.0/ratatui-widgets/src/lib.rs), [Backend trait](https://raw.githubusercontent.com/ratatui/ratatui/ratatui-v0.30.0/ratatui-core/src/backend.rs), [MIT license](https://raw.githubusercontent.com/ratatui/ratatui/ratatui-v0.30.0/LICENSE). Release aliases above were resolved to the recorded commit; a future import must retain that identity.

The [published 0.30.0 facade manifest](https://docs.rs/crate/ratatui/0.30.0/source/Cargo.toml.orig) was also read and contains the same unconditional core/widgets dependency declarations and facade feature switches; the calendar-default conclusion is not inferred solely from an unreleased branch.

**Selected proposed dependency surface:** use Ratatui's own modular packages, not a replacement UI library:

```toml
# Candidate only; not applied to any workspace manifest.
ratatui-core = { version = "=0.1.0", default-features = false, features = [] }
ratatui-widgets = { version = "=0.3.0", default-features = false, features = [] }
unicode-width = { version = "=0.2.2", default-features = false }
```

The public SDK/backend uses `ratatui_core`; consumers use its Terminal/layout/buffer plus `ratatui_widgets` tables/lists/paragraphs. Upstream widgets explicitly document direct use for finer dependency control. No compatibility facade/re-export or duplicate backend is proposed. Both libraries declare `#![no_std]` and `extern crate alloc`; core's default feature list is empty. No `std`, `layout-cache`, serde, palette, macros, portable-atomic, calendar, experimental or standard OS-terminal backend feature is requested. x86 already has native 64-bit atomics; absence of `portable-atomic` is not a proof that every resolved atomic path works.

**Important manifest trap:** `ratatui =0.30.0` defaults select crossterm, underline-color, all-widgets, macros and layout-cache; crossterm/termion/termwiz require `std`. Even `ratatui` with its own defaults off depends on `ratatui-widgets` without disabling that package's default `all-widgets`, which enables `calendar` and optional `time`. Adding a direct widgets dependency with defaults off does **not** subtract features unified through the facade. The selected modular route avoids that calendar dependency without modifying upstream or claiming a non-existent feature switch. Introducing the facade later requires a fresh feature-graph review.

**Observed nonoptional graph, not lock resolution:** core → bitflags, compact_str (defaults off), hashbrown, indoc, itertools (`use_alloc`, defaults off), kasuari (defaults off), lru, strum (derive, defaults off), thiserror (defaults off), unicode-segmentation, unicode-truncate (defaults off), unicode-width. Widgets → core, bitflags, hashbrown, indoc, instability, itertools, line-clipping, strum, unicode-segmentation, unicode-width. Host proc macros are executable build-time dependencies even though target code is `no_std`; they are covered by the later probe-execution admission, not silently exempted.

The Unicode-width release constraint is `>=0.2.0, <=0.2.2`; **0.2.2** is the proposed common width pin. Its [packaged manifest](https://docs.rs/crate/unicode-width/0.2.2/source/Cargo.toml.orig) records edition 2021, MSRV 1.66, MIT OR Apache-2.0 and default `cjk`; its [documentation](https://docs.rs/crate/unicode-width/0.2.2) says `no_std` and explicitly warns that width is not a guarantee of actual font shaping. `width`, not `width_cjk`, must implement the candidate ambiguous-width=1 profile; line/control processing remains outside width lookup. Ratatui's transitive reference may still activate `cjk`; that feature adds capability, it does not force callers to use CJK width.

**Concrete target gap:** Backend has an associated `core::error::Error` type, iterated changed cells, cursor/clear/size/window-size/flush operations; it does not own authenticated input, raw/echo guards, foreground rights or restoration. Implement those only through existing candidate D02 and `spec.md`, including a local tracked cursor rather than a terminal-query protocol outside `cellos-vt1`. No Unix tty/stdout shim is required by the trait. Native layout still uses f64 constraints through kasuari and widgets include clipping/chart arithmetic: disabled SIMD/SSE and soft-float linkage must be tested, not hand-waved away by `no_std`. [Kasuari 0.4.11's manifest](https://docs.rs/crate/kasuari/0.4.11/source/Cargo.toml.orig) and [lib](https://docs.rs/crate/kasuari/0.4.11/source/src/lib.rs) provide a verified no_std/MSRV-1.85/MIT-or-Apache reference inside the allowed `0.4` range; **that is not a selected transitive lock pin**. The [line-clipping 0.3.0 package](https://docs.rs/crate/line-clipping/0.3.0) exposes floating-point geometry and MIT OR Apache-2.0, likewise not a resolved pin. Actual allocations, missing soft-float helpers, selected versions and codegen remain probe outputs.
