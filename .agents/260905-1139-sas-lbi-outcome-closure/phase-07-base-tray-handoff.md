# Phase 07: BASE-01 Secured Dummy-Tray Handoff

> **Required — deviation-log:** Record every Decision / Deviation / Surprise immediately in § Deviation Log; use the smallest reversible option and escalate irreversible or contract-breaking changes.

## Overview
Deliver one identified, secured tray of dry inert closed dummy sample-carriers from named handoff station H-A to H-B in a controlled flat lab test area. The observable outcome is the same tray and carrier inventory verified at H-B, stationary and eligible for local handoff, with a traceable result—not an accepted travel command or software position estimate.

## Requirements
- Scope: BASE-01 only; one active workflow job shared across LAB-01, BASE-01 and ASSEMBLY-01. Composed steps retain that identity; reject other admissions until completion or explicit reconciliation closes it. Preserve job, tray, carrier, source/destination and immutable run/fixture/configuration identity; never silently replace a missing carrier or reassign an uncertain sample.
- H-A admission requires authoritative tray identity/inventory and secure-status observation, an eligible local safety condition, and stationary handoff. At H-B independently observe intended station arrival, stationary condition and retained tray security before permitting handoff and recording completion.
- Arm activity is prohibited during base motion in the first supported workflow. Base motion and LAB-01 execution are mutually exclusive; an arm parked/retained indication is an admission condition, not a substitute for local safety.
- No walking, jumping, stairs, self-balancing algorithm, full ROS/NPU port, autonomous experiment selection, hazardous samples or military/swarm behavior. Preserve the owner's wheeled two-leg concept; its exact mechanics, support and controller remain unselected. BASE-01 does not force legs versus wheels as mutually exclusive choices or select a BOM.
- Drafting can start now; 07A implementation/acceptance consumes the accepted 06A common contract rather than duplicating it. Native QEMU work does not require a physical lab robot; physical motion requires exact-device readiness below. Full phase remains incomplete until 07C passes; unavailable 07C is external-gated and unexercised, never passed.

## Architecture
- **Source facts:** `boards/raspberry-pi/3-model-b/board.rs:6-24` declares a Model B board and UART/timer/storage/I2C/SPI/GPIO/display/USB/Ethernet drivers; this is not a Model B+ identity reconciliation or a motor/brake/stability controller.
- **Source facts:** `cells/tests/bench/src/scenarios/control_loop.rs:19-24,41-60` measures periodic timeout jitter with a 50 ms probe; it does not sense position, command a motor, or validate physical closed-loop stability.
- **Source facts:** `cells/demos/robot-demo/src/main.rs:77-112` implements relay/sensor exercise with synthetic fallback. Neither its done banner nor `tests/integration/tests/robot-demo-e2e.rs:91-109` establishes tray movement or completion; do not copy fallback as physical evidence.
- **Source facts:** `cells/tests/bench/src/scenarios.rs:11-22` supplies per-scenario modules; `cells/tests/bench/src/main.rs:191-218` dispatches bench roles. `libs/ostd/src/fs.rs:52-81` uses owned file capabilities and requires reopen after VFS restart. Reuse these conventions and Phase05's real backend/oracles, not a new robot middleware platform.
- **Reported context:** QEMU and two owner-reported Pi3 B+ development boards exist; no robot, actuator, fixture or safety hardware is selected and no procurement is authorized. Prior GPIO/SPI loopback and I2C NACK evidence is not robot evidence (`.agents/260819-1416-port-common-drivers-g1-g2-g3/reports/evidence/phase03-rpi3-bcm-hardware-gates-20260820.md:16-35`).
- Logical flow: identify/secure at H-A → authorize bounded delivery → observe transit or uncertainty → observe H-B/stationary/secure → eligible handoff → persist result/readback. Freeze the precise handoff-observation method in the physical package; no command acknowledgement counts as physical completion.
- Shared Phase06 job/handoff semantics remain a private logical contract, not a public ABI/wire format. Bound queues, inventory and evidence capacity before Build; bind evidence to controller/observer instance and configuration, rejecting stale observations and requests.
- Crash, power interruption, lost observations or changed configuration during delivery yields `Indeterminate/ReconcileRequired`; inhibit automatic continuation, retain tray/job attribution, reconcile actual location/security locally, and require explicit re-enable. Invalidate old requests and trajectory/control state after configuration change. Memory/VFS snapshots do not establish tray position or restart-safe physical state.
- Local drive/brake/safety mechanisms must achieve the hazard-owner-defined independent safe disposition even with Cellos/Linux failed; merely stopping a Cell or removing torque is not generally safe. Missing such mechanisms blocks motion, not 07A/07B.

7. Record 07A, 07B and 07C independently and retain the physical gap. Neither a physical device substitution nor revised payload/controller/fixture inherits prior acceptance without reassessment.

## Security Considerations
Use local authenticated identities/capabilities with least privilege; shared workflow permission never overrides independent safety authority. No public/remote C2C enablement workaround, network command fallback or cross-board SAS pointers. A future cross-board transport needs a separately specified authorized boundary; existing local software witnesses do not authorize it. Preserve ADR0006/0007/0013 production, exact-device and independent-promotion gates; product-scope approval is not blanket Law1 approval.

## Risk Notes
Incorrect stop/torque-off behavior can drop a tray or destabilize a base; hazard review must define safe holding/retention rather than assume a software stop. A module boundary does not imply hazard independence. Missing hardware/controller/metrology blocks physical outcome only, never model work.

## Risk Assessment
Revert private scenario/image changes and remove only run-owned scratch resources to reverse software work. Software rollback cannot reverse a collision, dropped carrier, moved tray or stored energy; first use the independently specified physical safe-disposition procedure, inspect/reconcile identity and location, then explicitly re-enable. No snapshot restore or automatic inverse motion is a physical rollback.
