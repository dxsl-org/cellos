1//! Recoverable domain-aware user copy boundary (Spec 22, phase 03).
2//!
3//! This is the ONLY module allowed to touch user bytes. Every syscall-facing
4//! dereference goes through [`copy_from_user`] / [`copy_to_user`], which run a
5//! uniform two-pass transaction:
6//!
7//! 1. PROBE PASS (non-mutating): arithmetic range validation (null / overflow /
8//!    non-canonical / kernel-half), then a per-page permission check — private
9//!    roots consult their mapping ledger AND the live Sv39 PTEs; the shared
10//!    address space walks the currently active root. No bytes move, so any
11//!    failure here leaves both destinations byte-identical.
12//! 2. COMMIT PASS: the byte copy runs inside a per-hart recoverable fault
13//!    guard. For `CopyView::Domain` the CopyReader pin is held across the
14//!    whole commit and every page's PTE is re-walked under the pin before any
15//!    byte moves; because `unmap_private_page`/`unmap_grant_page` drain copy
16//!    readers BEFORE tearing down any PTE, an in-window fault is unreachable
17//!    through the public API and remains a recoverable `CopyError` (never a
18//!    panic). For `CopyView::Sas` the commit copies through user VAs under the
19//!    active shared root; on x86_64 under SMAP the guard window is the only
20//!    place the kernel touches a USER page (it sets RFLAGS.AC), while RV64
21//!    keeps `sstatus.SUM` set and AArch64 runs without PAN.
22//!    The guard alone does NOT make that recoverable: a retired Sas page is
23//!    re-mapped kernel-RW, which the kernel writes without faulting. The Sas
24//!    commit therefore runs under the `sas_lease` window, and every path that
25//!    retires a Sas user frame first unmaps it, flushes every hart, and calls
26//!    [`wait_sas_copies_quiescent`] (`task::stack::unpublish_user_frames`).
27//!
28//! The guard itself lives in `hart_local` (`user_copy_guard_*`). The RV64 trap
29//! handler routes guard-owned page faults to the helper's error label by
30//! rewinding `sepc`; everything else keeps its existing fatal path. No
31//! scheduler lock, no allocation, and no callbacks run inside the guarded
32//! window, and the window masks interrupts so a context switch can never carry
33//! a stale guard into another task (`clear_guard_for_context_switch` is the
34//! defense-in-depth backstop for that invariant).
35//!
36//! Layout: [`range`] owns the validated slice/view vocabulary,
37//! [`page_probe`] owns ledger + live-leaf validation, [`copy`] orchestrates
38//! the two-pass transaction, and [`guard`] arms the per-hart recoverable
39//! fault window around every byte movement.
