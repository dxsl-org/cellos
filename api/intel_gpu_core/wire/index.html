XE_GPU IPC transport (service id 21, CP1 D-G8): one DRM file operation per request, the xe ioctl carried unchanged.

The transport adds no GPU semantics (ADR-0033 G1, “no new GPU API”): the request code and the struct bytes are Linux’s. The one thing IPC cannot do in place is touch the client’s memory through the user pointers inside a struct, so the client declares the user ranges a request may touch:

  • an IN segment carries its bytes to the driver, which may read only inside it;
  • an OUT segment is a range the driver may write; the reply returns every write and the client applies it only inside a range it declared.
  • an EXPORT segment is not memory at all: it attaches one client-memory export lease (ExportDmaRange, syscall 437) to the request, the way an fd rides beside an ioctl. Its descriptor is {addr = export id, len = 0, flags = SEG_EXPORT} and nothing else; the driver maps it with MapDmaExport (438) and checks that the lease’s owner is the request’s attested sender. GEM_CREATE carries exactly one (CP1 D-G1 option B); every other request carries none.

Anything outside the declared segments fails with EFAULT, as a bad user pointer does.

Request (little-endian): op u8, segment_count u8, arg_len u16, file u32, request u32, reserved u32 (0), then segment_count × {addr u64, len u32, flags u32}, the arg bytes, and the bytes of each IN segment in order; the counts give the frame length. Reply: errno u32 (0 = success), value u32, arg_len u16, write_count u8, reserved u8 (0), reserved u32 (0), then write_count × {addr u64, len u32, reserved u32 (0)}, the arg bytes and the bytes of each write in order. The layout is recorded in docs/abi-boundary-records.md.
