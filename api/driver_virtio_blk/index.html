VirtIO-blk Driver Cell — Tier-1 Privileged Driver Cell.

riscv64 / aarch64: probes VirtIO MMIO slots for a Block device (type 2), claims exclusive MMIO via sys_request_mmio and publishes BlockDevice::Mmio { base }. x86_64: claims a virtio-blk PCI function by vendor:device (1af4:1042, then 1af4:1001), drives it through virtio-pci-transport with polled queues and publishes BlockDevice::Pci { bdf }. Either way the virtqueue is initialised via virtio-drivers and the cell serves the DrvRequest sector-I/O protocol (identical wire format to the NVMe Driver Cell — VFS speaks ONE block protocol) to the registered VFS only. Replaces the kernel’s virtio_blk.rs driver per the Kernel Boundary Law (G2 loader redesign).

§Device ownership

The RequestMmio claim is the only gate on a device: no other driver drives a block slot, and initialising the transport resets the device, so a slot left at DRIVER_OK (by firmware, or by a predecessor cell whose slot the kernel reset when it died) is taken over. A slot still held by a predecessor awaiting reap is retried; the cell exits when no block device can be claimed.

§Law 4 exception

src/mmio.rs, src/hal_x86.rs and src/io.rs use unsafe for the virtio_drivers::Hal impls, DMA bounce copies, the non-blocking request calls and the MMIO probe reads. No other module does.
