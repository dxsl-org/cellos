Expand description

Input routing and mouse position state owned by the compositor.

Fields§

§input_tid: usize

TID of the input service cell (0 = not yet connected).

§compositor_tid: usize

Registered TID for the compositor’s input endpoint.

§mouse_x: i32

Logical mouse cursor position (updated from MouseMove events).

§mouse_y: i32§pointer: PointerRouter§hw_cursor: bool

True when the VirtIO GPU hardware cursor was successfully uploaded at startup. When true, MouseMove issues GpuCursor(move) instead of triggering a full software repaint via pending_dirty.

§launch_armed: bool

Set by a left press on a Panel (the single-owner desktop shell, e.g. a taskbar launcher) and cleared by the next pointer press or key: until then one newly created window may take focus from the panel, so an app the user just launched from the shell gets the keyboard.

pub fn request_focus(&mut self, owner: usize, cap: u64) -> bool

Give keyboard focus to a client’s own surface on a client request (raise, view selection). A client may never take focus from another client: only a pointer press, which the compositor routes itself, moves focus between owners. Nobody focused means keys reach the console shell, so a surface may still take focus then; it is on top and the user sees where keys go.

Source

pub fn may_focus(&self, owner: usize) -> bool

Whether a client request from owner may move keyboard focus: it holds the keyboard already, or nobody does.

Source

pub fn focus_new_window(&mut self, owner: usize, cap: u64) -> bool

Focus rule for a newly created window: Self::request_focus, plus one window right after the user pressed on the desktop shell’s panel (the launch gesture). The first new window after that press spends the grant.
