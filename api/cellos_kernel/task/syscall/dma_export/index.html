Module dma_export 

Source
Expand description

Client-memory DMA export leases: ExportDmaRange = 437, MapDmaExport = 438, RevokeDmaExport = 439 (ADR-0033, CP1 cp1-gpu-kernel-abi.md §5-§6).

A client Cell (the owner) exports a page-aligned range of memory it owns to the live bound provider of a service in DMA_EXPORT_SERVICES (the holder). The holder maps the export into its own VT-d domain at a kernel-allocated IOVA window in [2^38, 2^39) and programs that IOVA into its device. The kernel alone revokes: it clears the window’s leaves and drains the domain IOTLB, and only an acknowledged drain releases the owner’s range. It never waits on the holder (D-G5).

§State machine

437 ──► Live{unmapped} ──438──► Live{mapped} ──439/owner death──► Revoking
           │                       │                                  │
           └──439/owner death──────┴──holder domain revoked──► dropped ◄─ ack

Revoking keeps the owner range locked (and, after owner death, its frames in quarantine under ReleaseKey::DmaExport) until an invalidation is acknowledged; retry_pending repeats it on every scheduler pass.

§Locks

EXPORTS is taken under no lock but IOMMU_CLEANUP_SERIAL (holder hook): IOMMU_CLEANUP_SERIAL → EXPORTS → grant table → SCHEDULER → pin REGISTRY / EXPORTS → VT-d UNITS. The rank table lists them in that order (sync/rank.rs: IOMMU_CLEANUP_SERIAL, DMA_EXPORTS, PAGE_GRANT_TABLE, REG_GRANT_TABLE, SCHEDULER, …), which closes the inversion the census found (F7: DMA_EXPORTS used to rank after the grant tables it takes). Every lease transition happens under it, so 437/438/439, owner death and holder death are serialized. No frame is freed under it: an export’s released owner frames ride out in the KernelPlatform and are freed once EXPORTS is dropped (FRAME_ALLOCATOR/KERNEL_ROOT used to be taken under it).
