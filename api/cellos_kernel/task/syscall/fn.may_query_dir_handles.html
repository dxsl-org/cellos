fn may_query_dir_handles(caller_id: usize, target_cell: u64) -> bool
Expand description

May caller_id read the kernel’s provenance record for target_cell?

Two callers have a reason to: the filesystem service, which must decide whether to bind the set, and a cell asking about itself. Anything else enumerating another cell’s grant is reconnaissance with no legitimate use.

The filesystem service is identified by the service registry rather than by name, because a cell’s name comes from a spawner-chosen path hint and is therefore forgeable; registering a well-known service id is SpawnCap-gated and is not.

Lock order SCHEDULER → REGISTRY, matching Scheduler::reap; REGISTRY is a leaf and is never held across a scheduler acquisition.
