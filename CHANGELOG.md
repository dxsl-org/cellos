## [Unreleased]

### 🚀 Improvements
- tier3/Raspberry Pi 3: non-VHE EL2 monitor giữ host Cellos ở EL1 và Cells ở EL0; QEMU `raspi3b` đã chạy monitor smoke HVC/Stage-2 MMIO/IRQ/preemption, boot Alpine Linux ARM64 tới prompt `~ #` và thực thi `echo PI_TIER3_EXEC_OK` qua PL011. Sửa SPSR EL0 AArch64, timer C1 trễ hạn, world-switch SP_EL0, HVC PC và đường ID-register Cortex-A53; thêm GICv2 mềm, PL011 PrimeCell ID/RX, fixed-clock DTB và image SD 1 GiB có MBR P1–P4 canonical/P2 cell table rỗng. Chẩn đoán virtio-blk kẹt sau `[vda]`: DTB SPI 17 là GIC INTID 49, nhưng backend phát INTID 17 nên lần đọc phân vùng không thức dậy; chuẩn hóa SPI 16–20 cho ARM, giữ IRQ x86. SD profile gói thêm module ext4 từ modloop Alpine đã pin, initramfs tự nạp virtio/ext4 và mount `/dev/vda` ở `/mnt/disk`. Guest ghi `PI_DATA_123456`, sync và đọc lại sau QEMU reboot dùng cùng image; bản ext4 trích từ SD cũng chứa marker. Boot gate SD nay yêu cầu mount và shell. ARM `virt` regression phát hiện đường EL2 first-Cell dùng `SPSR_EL2=0x14` (AArch32) gây illegal return `EC=0x0e` trên QEMU Cortex-A72; đổi về AArch64 EL0t (`0`) và machinery gate PASS. QEMU-TCG Pi vẫn in soft-lockup warning ở đầu boot; lần thử TFTP vật lý và giới hạn của nó được ghi ở mục tiếp theo.
- tier3/RPi3 physical TFTP: first trial verified the full U-Boot transfer, CRC and EL2 entry but failed the HVC handshake; moving initialization before EL1 enables WB caching made the next physical run report `HVC ready=true`, `hvc_result=0x0`, `op0_seen=true`. Its *first guest* smoke still read `Unknown { ec: 0, iss: 0 } pc=0 esr=0`, so `HypervisorCap` stayed closed and Linux has **not** booted on Pi. Signed Input/DWC2/LAN9514 Cells now start, but the board enumerated only the `0424:ec00` Ethernet function before NYET/STALL on other hub ports and `[usb-hid] no HID device attached`; no keyboard success is claimed. A board probe then returned EL2's first guest entry, Stage-2 descriptors, instruction and trap ESR/ELR through HVC independently of EL1: EL1 held entry `0x40000000`, instruction `0xd2800540` and written descriptors while MMU-off EL2 read entry `0`, zero descriptors and faulted at PC `0` with `ESR 0x82000005` — EL2's uncached accesses and EL1's Normal-WB cached view did not agree. The monitor now installs matching Normal-WB/Inner-shareable EL2 identity translations before publishing readiness, after validating code, vector, stack, root and Device-MMIO leaves (`monitor_root_valid`, which also rejects a firmware WXN policy rather than weakening permissions). The rebuilt 60,538,944-byte uImage passes the QEMU `raspi3b` gate with EL1 and EL2 agreeing byte-for-byte (`entry=0x40000000 insn=0xd2800540 exit=[0x5a000000,0x40000008,irq=0]`), `HVC/MMIO/VI/PREEMPT smoke PASS; HypervisorCap open` and the Alpine guest shell; it is deployed as the TFTP root's `cellos.uimg` with the previous payload kept as `cellos.uimg.before-coherent-mmu-cc2baf12`. **Emulator evidence only** — the physical EL2 coherence row and the DWC2 split/keyboard diagnosis still await the next board trace, and no keyboard success is claimed.
- tier3/x86 guest-app gate: **ưu tiên CPython thay vì nginx làm oracle ứng dụng trong CI.** Trong guest Alpine 128 MiB, `apk add python3` bị OOM-killer giết khi giải nén; profile `alpine-wide` dành riêng cho workload tăng guest RAM lên 256 MiB, còn Alpine mặc định 128 MiB và Ubuntu root-on-blk 512 MiB không đổi. Gate `scripts/qemu-x86-python-gate.sh` dựng initramfs riêng, cài CPython qua HTTPS từ Alpine v3.21, chạy JSON→CSV với `decimal`/`csv` và cho một Python subprocess đọc kết quả đã đối chiếu; đã PASS 3/3 lượt QEMU-TCG 10.2.0. CI chạy Python trước, nginx sau làm regression phụ trong cùng job; không diễn giải QEMU thành chứng cứ board hay CSV trên tmpfs thành tính bền qua reboot.
- tier3/Python gate observability: `apk add python3` nay in tiến trình cài qua UART thay vì chỉ ghi file trong guest (khi outer timeout, file đó không thể đọc); `QEMU_NET_CAPTURE` cho phép lưu pcap qua `filter-dump` nếu cần điều tra HTTPS. Một lần với `BOOT_WINDOW=1000` chỉ đi tới DNS rồi hết cửa sổ, không có pcap nên chưa xác định khâu treo; bốn lần tiếp theo với 1200 s đều PASS, hai pcap thành công thấy ~20 MiB TLS trong 181/411 s. Không gắn timeout này với sửa `seg_max` khi guest Python không sử dụng virtio-blk.
- tier3/virtio-blk + vfs (tiếp P1): **ba lỗi tách biệt lộ ra khi đo, đã sửa, mỗi lỗi có bằng chứng riêng.** (1) `blk_flush` dùng ngân sách IPC cơ sở 200 tick — mức chỉ đủ cho một round-trip 4 KiB — trong khi một flush phải để VFS đẩy toàn bộ trạng thái dirty qua block device, nên flush chậm-mà-**đúng** bị timeout: `[hv-blk-host] request failed type=4 sector=0 buffers=2 status=1`, guest `dd … conv=fsync` báo `block-write` dù dữ liệu đã nằm trên đĩa (host-side marker check sau run1 vẫn PASS). Flush nay dùng `chunk_timeout_ticks(VFS_GRANT_CHUNK)` và in lý do khi hỏng. (2) `used.len` của virtio-blk read nay theo spec §2.7.8 — payload + status byte, trước luôn báo 1; Linux không phụ thuộc giá trị này (lane xanh cả hai cách) nhưng VMM thì phải công bố đúng. (3) Fixture e2e đọc marker với **page cache đã xoá** (`drop_caches`): một trang cache cũ có thể che device trả sai — hoặc tự trở thành câu trả lời sai — và chính điều đó làm lane xanh/đỏ thất thường. Kèm hai chỗ quan sát được giữ lại có biên: NVMe driver cell in `[nvme] io error opc=2 lba=…` (các read vượt namespace 256 MiB — thiết bị trả lỗi là đúng, VFS retry 3 lần hấp thụ; 3 dòng mỗi boot, timeout luôn log) và `blk-router` phân biệt send/recv lỗi với việc cell trả khác 0. **`seg_max` vẫn không được quảng cáo**: bốn lần chạy gần nhất với nó đều đỏ ở boot thứ hai, kể cả khi marker đọc bằng cold cache. Bốn chữ ký chưa đóng (short-read, zero-khi-`seg_max`, flush ngắt quãng, boot Cellos không tới evidence guest) nằm ở `.agents/TODO.md` kèm bước kế.
- tier3/virtio-blk + vfs: **một request đĩa không còn bị cắt thành từng chunk 4 KiB, và không còn lớp copy trung gian nào.** Đường persistent cắt `n.min(4096)`, rồi với *mỗi* chunk: cấp grant → share → gọi VFS → copy grant ra `tmp` rồi copy `tmp` vào guest RAM (đọc), hoặc copy guest RAM vào `tmp` rồi vào grant (ghi); phía VFS cũng chặn cứng `size.min(4096)` / `bytes > 4096` và tự copy qua một `Vec` trung gian. Nay hai phía dùng chung `api::ipc::VFS_GRANT_CHUNK` (64 KiB) và **gộp theo cả request**: cell gom/trải trực tiếp giữa các descriptor của chain và grant (`scatter_to_guest`/`gather_from_guest`), VFS đọc/ghi thẳng vào grant, không `Vec` bounce ở phía nào. `unsafe` của cả hai phía nằm trọn trong `ostd` (`GrantHandle::with_bytes`/`with_bytes_mut`, `grant::with_shared_bytes`/`with_shared_bytes_mut`) nên hai cell vẫn qua F1 gate mà không cần thêm entry allowlist. Grant lấy từ frame liền nhau nên `alloc_chunk_grant` giảm nửa dần khi cấp phát thất bại, **sàn một byte** — request nhỏ hơn một trang (ghi một sector, đuôi chain) vẫn phải chạy, và đúng lỗ đó làm lane hostile đỏ ở kịch bản recovery-write cho tới khi sửa; ngân sách IPC của chunk nay tỉ lệ theo kích thước (`chunk_timeout_ticks`) thay vì cố định 200 tick vốn chỉ đủ cho 4 KiB. Kèm dòng quan sát `[hv-blk] read|write bytes=… chunks=…` cho mọi request ≥ 64 KiB. `seg_max` **không** được quảng cáo: khi bật, guest gửi request nhiều segment rồi lần đọc sau chính sector đó trả về zero (device đã ghi đúng byte vào frame của descriptor — `ReadGuestMemory` đọc lại thấy marker — không request nào kết thúc bằng `VIRTIO_BLK_S_IOERR`, ảnh đĩa trên host vẫn còn dữ liệu, nhưng `dd if=/dev/vda` của lần boot sau đọc ra zero). Đây **không** phải lỗi của phần batching: code cũ (chưa có P1) + `seg_max` cũng hỏng, và `seg_max: 2` cũng hỏng, nên bug nằm ở cách device model phục vụ chain nhiều descriptor; lý do khoá feature + danh sách giả thuyết đã loại trừ được ghi ngay tại `config_read`, việc mở lại nằm ở `.agents/TODO.md`. Kiểm: `scripts/qemu-x86-virtio-e2e.sh` PASS (marker bền qua hai boot), `scripts/qemu-tier3-hostile-runner-x86.sh` PASS (27 kịch bản + recovery write đọc từ host), lane ARM64 machinery PASS; bisect cho thấy đúng thay đổi cell + `seg_max` là nguyên nhân, và mọi lane xanh trở lại khi tắt `seg_max`.
- vfs/page-cache: **ngân sách cache suy từ heap của cell, và ghi theo thứ tự device-trước-cache.** `MAX_CACHE_BYTES` từng là 4 MiB cố định — đúng bằng toàn bộ heap 4 MiB của cell (`VFS_HEAP_BYTES` nay là hằng số dùng chung) — nên cache đầy arena trước khi eviction kịp chạy: guest chỉ cần chạm ~1 MiB sector là cell chết với `OOM: cell heap exhausted` (đo được trong lane e2e khi tôi thêm probe I/O). Cache nay lấy một phần tư heap. Cùng chỗ đó, `write_sector` ghi device *trước* rồi mới đưa entry (luôn sạch) vào cache: trước đây entry được đánh dấu dirty rồi flush, nên khi flush lỗi mà entry còn dirty thì một lần eviction sau đó có thể nuốt mất sector chưa ghi — `debug_assert!` canh bất biến này là no-op ở release, và đó là đường làm marker bền đã mất tích trong một lần chạy. Thêm nữa, `read_raw_sector`/`write_raw_sector` nay thử lại 3 lần: một lần lỗi block thoáng qua trước đây biến thành *short read*, và tầng trên báo lỗi I/O cho guest từ hư không.
- cells/tier2-grant-pair + init + aarch64 lane: **the phase-03 step-5 grant pair now runs end-to-end on AArch64.** That image never becomes interactive (its own test root exits the VM before the shell's first prompt), so the RV64 handoff — the runner reads the owner's `HANDOFF` line and types the ids into the receiver's command line — cannot be reused. `app-init` gained an opt-in `tier2-grant-pair` feature that launches the pair from the boot order on the two reviewed init-launch edges whose services that image does not build (`/bin/silo` owner, `/bin/net-broker` receiver; the feature is a compile error together with `development-silo-provider`/`c2c-broker`, and a brand-new `/bin/<name>` would still need a kernel launch-profile + boot-ceiling row), publishes each generation's mode through the existing staged-argv surface, and starts the next generation only after the previous one's terminal fault. The ids are no longer console-driven at all: they are kernel-assigned *after* the owner starts, so a receiver without them asks the owner over the pair's own `Send`/`Recv` channel (`WANT_IDS` → `ACK` + four little-endian `u64`s) — no ABI change. Both cells tag every marker with the architecture they were built for (`S22-RV64-*` / `S22-AARCH64-*`); the AArch64 lane already refuses another architecture's tag as evidence. `scripts/qemu-aarch64-test-hooks.sh` now requires the pair's markers and accounts for **every** cell fault in the boot — the announced NULL store at `addr=0x0` plus exactly the five receiver store faults classified to the handoff ids (1:2:1:1) and announced before each one — so an unannounced, unclassified or extra fault still fails the lane. Verified: `bash scripts/build-aarch64-test-hooks-ci.sh` then `bash scripts/qemu-aarch64-test-hooks.sh` → exit 0 with `S22-AARCH64-GRANT-PAIR-OWNER: PASS`; handoff `id1=1114615808 id2=1114624000 id3=1114628096 id4=1114632192` faulted at `0x426fb000`, `0x426fd000`×2, `0x426ff000`, `0x426fe000` (ReadOnly and downgrade faults are permission faults `cause=0x9200004f`, the revoked ones translation faults `cause=0x92000046`), and `scripts/qemu-native-domain-test.sh --case grant-pair --harts 1` still PASSes with `faults=1:2:1:1`.
- kernel/loader + init: **x86_64 now enters a real Tier-2 domain on one CPU too.** `switch_ordering_qualified()` reopened x86_64 for `test-hooks` builds only, the production pin now const-asserts that no production AArch64 *or* x86_64 build can qualify, and `enable_for_boot` refuses the posture on a boot whose kernel CR3 was never published (`memory::paging::init_kernel_paging_x86`), the x86 counterpart of the AArch64 EL2 refusal. A new lane, `scripts/x86/qemu-domain-test.sh` + `scripts/build-x86_64-domain-test-ci.sh`, packs `/bin/tier2-smoke` + `/bin/tier2-exploit` into an override VIFS1 ramdisk, launches them from the boot order (`tier2-entry` init), and asserts admission, the real admission (`[domain] admitted cell 'tier2-smoke' to Tier 2 Paged Domain (CR3 isolation)`), the **live CR3** read from inside the domain's own kernel context (`S22-X86-DOMAIN-LIVE: PASS cr3=... root=... pcid=... pcid_usable=... kernel_cr3=... domain=... generation=...`), the deliberate NULL-store fault contained (`[fault] Cell ... terminated: ... addr=0x0`, exactly one, boot survives), teardown with frames released and nothing quarantined (`DOMAIN-FRAME-RELEASE: PASS ... quarantined=0`, `S22-X86-DOMAIN-TEARDOWN: PASS releases=1 quarantined=0`), and shell recovery after the fault (a `ps` typed into the still-interactive shell, answered with a second prompt). Executed: TCG (`qemu64,+pdpe1gb`, exit 0 - PCID unusable, domain CR3 untagged, `pcid=0 pcid_usable=false`) and **KVM** (`-accel kvm -cpu host`, exit 0 - `CPUID pcid=true invpcid=true CR4.PCIDE=1`, live `cr3=0x11c9001 root=0x11c9000 pcid=1`), so the CR3 **and** the PCID tag path are both real. Not proven: an x86 *production* image carries no domain-class cell, so its runtime denial is pinned by the const-assert and by the posture line `Tier 2 admission: DISABLED (development profile, phase-02 switch-ordering gate)`, which `scripts/qemu-x86_64-test.sh` now asserts on the production image.
- kernel/loader + init: **AArch64 now enters a real Tier-2 domain on one PE.** `switch_ordering_qualified()` reopens AArch64 for `test-hooks` builds only, a const-assert pins that no production AArch64 build can qualify, and `enable_for_boot` refuses the posture on an EL2 host, where `__switch_el2` has no root argument. The test-hooks image carries `/bin/tier2-smoke` and `/bin/tier2-exploit` (both `PROTECTION_CLASS_UNTRUSTED`, so the loader classifies them domain-class) and the reviewed init launch edge for them. `scripts/qemu-aarch64-test-hooks.sh` asserts the admission posture, the real admission, the domain's **live** `TTBR0_EL1` with a non-zero ASID read from inside the running domain's kernel context (`S22-AARCH64-DOMAIN-LIVE: PASS asid=1 root=… ttbr0=0x10000418cd000`), a contained NULL-store fault the boot survives to its terminal marker, and the teardown release (`[selftest] DOMAIN-FRAME-RELEASE: PASS … quarantined=0`, `S22-AARCH64-DOMAIN-TEARDOWN: PASS releases=1 quarantined=0`). The fixtures are launched from the boot order, not a prompt: this image's shell sleeps ~2 s before its first prompt while its own test root exits the VM at ~4.5 s, so no interactive window exists.

- cells/service-net + net-tools: **Cellos ra internet thật, không chỉ tới host mock.** `NetRequest::Resolve` trước đây luôn trả `Err(0xFF)`; nay net cell sở hữu một smoltcp `dns::Socket` (`cells/services/net/src/dns.rs`) và trả `NetResponse::Addr` theo đúng một thứ tự: IPv4 literal → alias SLIRP (`gateway`/`host`/`dns`/`localhost`) → truy vấn A-record UDP tới DNS server **do DHCP cấp** (option 6, fallback 10.0.2.3), dùng retransmit/backoff và theo CNAME của smoltcp, trần 3 s mỗi lookup (log `[net] DNS server: <addr>`). `curl`, `wget`, `nc`, `mqtt`, Ocel và binding `vnet.*` của Lua bỏ bảng alias riêng, `parse_ipv4` riêng và DNS client cục bộ để đi qua đúng một resolver này (binding Lua hiện **chưa** được wire vào module tree của cell lua — `main.rs` không có `mod bindings_net;` — nên chưa script nào chạm tới; sửa để không còn bản sao trôi dạt khi nó được bật lại). Tầng C/POSIX cũng có tên miền: `gethostbyname` trong `libs/api/src/services/posix/net.rs` trả `struct hostent` từ chính resolver đó (static storage đúng hợp đồng POSIX, không cấp phát), và witness `posix-shim-test` chứng minh `gethostbyname("gateway")` → 10.0.2.2 rồi `connect` qua chính địa chỉ vừa resolve (`POSIX-DNS: OK`, chạy trong test `posix_shim_net` đã có trong CI allowlist; hợp đồng shim sinh lại: 201 export). Cùng chỗ đó, `send` của shim thôi đếm 20 lần yield — quan sát được là `POSIX-DNS: FAIL send ret=-1` khi handshake chưa xong — và nay bound theo đồng hồ (`GetTime` op 1, 5 s) với trần vòng lặp làm chốt chặn. Hai lỗi thời gian lộ ra khi chạy thật ra internet: vòng gửi/nhận của `curl`/`wget` bị chặn bằng *số vòng lặp* 500 nên một round trip WAN (ARP + SYN + handshake + server) tiêu hết budget trước khi request được gửi ⇒ `curl: empty response`; nay là budget theo đồng hồ (`GetTime` op 1, 30 s) cộng trần vòng lặp. Kiểm chứng: `curl http://example.com/` trong QEMU RV64 qua SLIRP trả `HTTP/1.1 200 OK` + body thật, `wget http://example.com/ /tmp/internet.txt` ghi 423 byte rồi `vcat` đọc lại được `Example Domain` (`network_reaches_the_internet_by_name`, gate theo internet của host vì SLIRP chuyển DNS/TCP của guest cho host), và `network_resolve_answers_hostname_through_the_service` (deterministic: alias `gateway` + mock host). 3 host unit test trong `cargo test -p service-net` khoá literal/alias.
- kernel/init + service_table: **budget chống crash-storm của `init` đã thực sự có hiệu lực.** `supervisor.rs` so cửa sổ 1 000 đơn vị với `sys_get_time()` = `GetTime` **op 0** (counter thô, 10 MHz `mtime` trên RV64) thay vì scheduler tick (op 4) ⇒ cửa sổ thực ~0,1 ms, roll mỗi lần exit, `restart_count` không bao giờ đạt `MAX_RESTARTS_PER_WINDOW` ⇒ service crash-loop được respawn vô hạn (Spec 12 §4.3 "≤5/~10 s rồi bỏ mặc" không có hiệu lực). - kernel/sched: **an RT sender woken by a consume now preempts its target hart.** `wake_sender_token` readied the sender and called `push_ready` but discarded the priority it returns, so no preemption was ever requested and a RealTime sender waited for the next timer tick; every other wake path (`ipc_send`, `ipc_publish_input`, `ipc_reply`) already paired the two calls. `pend_preempt_if_needed` also decided from the *calling* hart's running priority while targeting `HART_RT`, so a busy waking hart swallowed the request and an idle one sent a needless IPI — the predicate now reads the target hart's running priority. Witness `S22-RV64-RT-WAKE` (runner case `rt-wake`, `--harts 2`): the fixture holds `SCHEDULER` across its body, pins the target hart on a Normal occupant and the waking hart on a RealTime one, and asserts the wake lands the sender on the target hart's ready queue with exactly one pended preemption, that a stale delivery token pends none, and that the decision follows the target hart. Red with the wake call reverted (`h2-rt-wake-xiIlSU`: `pended=false`), red with both hunks reverted (`h2-rt-wake-3qm6mA`: `pended=false target_hart_decides=false`), green after. - kernel/aarch64: **the AArch64 test-hooks kernel builds and boots again.** The lane had been red on the unmodified tree (8 errors, then 14 once the imports were narrowed) because the RV64-only test scaffolding carried only `#[cfg(feature = "test-hooks")]`: `smp::online_hart_count` (riscv64 SBI bring-up), `mapping_state`'s leaf comparison (`u64 & usize` between the AArch64 leaf word and the RV64 constants), the `user_copy` fault-injection helpers, and the admission/address-space/switch/futex fixtures' helper functions were all compiled on AArch64 and then reported as missing, unused or dead. - kernel/memory: **an unmapped page is invalidated before its frames can be reused.** `unmap_private_page` released the owned leaf frame and pruned its table chain without invalidating anything at all, and `unmap_grant_page` freed the pruned tables before its flush — so a hart that still held the translation could walk a table frame already handed to another root, or read a leaf whose contents had been reused. Both now detach the pruned tables (and, for a private page, the leaf) into locals, drop the table/ledger locks, run the page invalidation (local sfence + remote RFENCE on RV64), and only then release the frames — the order `unmap_existing_task_stacks` already used. Witness `S22-RV64-UNMAP-ORDER` (runner case `unmap-order`): red before (`h1-admission-7j4HaI`: no flush observed for the unmapped page), green after.
- kernel/asid: **two live private roots can no longer share one architectural tag.** `AsidLease` handed out tags by masking a monotonic counter into the tag space: after a wrap it returned tag 1 without checking whether tag 1 was still live, and the next acquisition returned tag 1 again — two live roots on one tag, so a stale TLB entry of one could resolve inside the other. Tags now come from a bounded pool (`MAX_LIVE_ASIDS` = 256 slots, value `slot + 1`, tag 0 reserved for full-flush mode), a slot is returned to the pool only **after** local and remote invalidation for that value completes, exhaustion makes `AddressSpaceBuilder::build` refuse the domain (`OutOfMemory`, no SAS fallback) instead of reusing a live tag, and a slot whose recorded owner does not match is retained with a warning rather than freed. `asid_width()` documents the 12-bit x86 PCID / 16-bit RV64-AArch64 limit and the allocator asserts every value fits. Witness `S22-RV64-ASID-LEASE` (runner case `asid-lease`): red on the counter (`h1-admission-SKd2ze`: `distinct=false width=true first=1 second=1`), green on the pool.
- kernel/grants + snapshot: **fail-closed containment for the unqualified paths.** Every `Grant*` entry point that names a private-root task now refuses at the common syscall gate — `GrantAlloc`/`GrantRegister` cannot complete an owner mapping (their ungated path also published the frames USER in the shared root) and `GrantSlice` published a receiver PTE with `shared_to`'s rights ignored and no revoke path, so the kernel denies before a table row, PTE, pin or frame exists. The refusal is the per-op alloc-safe sentinel (`0` for alloc/register, because `ostd::syscall::sys_grant_alloc` reads any nonzero return as a grant id; `usize::MAX` for slice), SAS→SAS Tier-1 grants and copied IPC are untouched, and a *live* grant record naming a private-root owner or receiver blocks domain admission until drained. Tier-2 admission on AArch64/x86_64 stays closed until phase 02 proves the ordered root switch on one CPU (RV64 keeps launch + copied IPC; `enable_for_boot` now refuses an unqualified backend, with the posture logged at boot). `serialize_snapshot`/`try_restore` are gated behind the new `snapshot-qualified` feature (off in every default image): capture refuses before its first write, warm boot cold-boots and clears a stale header so an older image cannot replay it. Witness: new `S22-RV64-GRANT-GATE` boot fixture through the public `handle_syscall` path with a real `TaskAddressSpace::Domain` task — red on the pre-gate kernel (ALLOC/REGISTER/SHARE/SLICE/FRAMES all FAIL) and green after, run as `scripts/qemu-native-domain-test.sh --harts 1 --case grant-gate`; `tier2-smoke` now asserts the denial instead of the retired positive grant leg.

- kernel/domain: **non-RV64 switch completion is now an explicit incoming hook, and every unmap releases frames only against a tag-targeted acknowledgement.** The old code inferred "the safe root is installed" from `current_domain() == 0`, which is false exactly when it is needed — a safe-root transition does not clear the id until `acknowledge_safe_root` runs. `task::complete_incoming_switch` (`kernel/src/task.rs:918-928`) now runs in the *incoming* context after `Context::switch_with_root` returns, consumes the plan's `safe_root_pending` flag, acknowledges the safe root, releases the displaced root's execution pin and resets the user-copy guard. `unmap_private_page`/`unmap_grant_page` reserve the VA, flush the **root's own** tag (not the currently active kernel root), and release the leaf and pruned tables only after `flush_asid_and_await` succeeds; a missing acknowledgement quarantines them, keeps the VA reserved and returns `InvalidationUnacknowledged`, and `AddressSpace::drop` releases the tag before any frame. Witness, AArch64 one-PE lane (exit 0, `[vfs-test] Results: 96 PASS, 0 FAIL`): `S22-AARCH64-ROOT-SWITCH: PASS … outgoing_stack_shared=false safe_root_consumed=true`; host lane 145/145. The tag release contract rests on ASID-targeted invalidation, which AArch64 private-root leaves cannot yet meet (`PTE_nG` is never set), so that arm uses a full `vmalle1is` stopgap and AArch64 admission stays refused.
- kernel/x86: **the PCID/INVPCID runtime gate probed the wrong CPUID leaf.** It read `CPUID.01H:ECX[12]`, which is FMA, so it reported INVPCID present on almost every CPU — including ones without it — and a nonzero PCID could then be used with no way to invalidate a single context. The probe now reads `CPUID.07H:EBX[10]`, a nonzero PCID additionally requires INVPCID (a CR3 reload only invalidates the current tag), `CR4.PCIDE` is set only when the boot CR3 has zero low bits, and a firmware-set PCIDE is cleared after selecting tag 0; `flush_asid` uses type-1 INVPCID for a named context and `flush_all` type 3. Witnesses on the current tree: TCG `X86_EXPECT_PCID=0` → shell + `PCID disabled (CPUID pcid=false invpcid=false, CR4.PCIDE=0, CR3=0x59000 …)`; KVM `X86_EXPECT_PCID=1` → shell + `PCID enabled (CPUID pcid=true invpcid=true, CR4.PCIDE=1, CR3=0x59000)`; `cargo test -p hal-x86 --target x86_64-unknown-linux-gnu` 12/12 with three new policy tests. The `INVPCID` instruction path stays unexecuted while no x86 domain can be admitted.
- kernel/snapshot: **writer and reader now agree on one format (internal v2), one checksum and one durable state machine.** The old pair disagreed by construction: the writer hashed frame bytes only and wrote allocated frames in ascending frame index, the reader hashed header + payload and reconstructed a dense `pa_base + index * 4096` run. `kernel/src/snapshot.rs` is now `SNAPSHOT_FORMAT_VERSION = 2` with a 512-byte header in the reserved MBR partition P3, an explicit `SnapshotRun { pa: u64, frame_count: u32, flags: u32 }` inventory, the payload in inventory order (the reader never reconstructs a dense run), and one canonical `crc32(header.canonical_bytes() || inventory || payload)` with the CRC field zeroed, produced by a single shared helper. The on-disk state machine `EMPTY → WRITING → COMMITTED → CONSUMING → CONSUMED` orders the writes durably (WRITING header + flush → inventory → payload → flush → COMMITTED header + flush; validation → durable CONSUMING → replay → CONSUMED), a reboot that sees WRITING/CONSUMING/CONSUMED refuses and erases, and a failure after replay began returns `RestoreOutcome::FatalMixedRam` and resets (`halt_mixed_ram`) instead of continuing a cold boot on mixed RAM. Verified with a test-only in-memory fake block device (volatile write-back cache, per-ordinal write/read/flush fault injection, torn sectors, crash-after-flush, sparse RAM model): `cargo test -p cellos-kernel --target x86_64-unknown-linux-gnu` **145 passed** (26 new snapshot tests), with a red witness from a throwaway transcription of the legacy pair (`Err("crc")`; dense `{base+0,+1,+2,+3}` instead of `{base+0,+3,+4,+10}`). `QUALIFICATION_ENABLED = cfg!(feature = "snapshot-qualified")` is untouched, so capture/restore still refuse and `docs/specs/03-runtime.md` §4 now documents this contract instead of the retired 40-byte `system.img`/FAT16 layout and the unwitnessed sub-100 ms claim.
