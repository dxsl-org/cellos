C2C Phase 03: concurrent input streaming under pending RPC witness (2026-10-09)

Scope: new fixture witness in cells/tests/bench/src/scenarios/local_service_lifecycle.rs and bench-probe role dispatch (`c2c-input-provider`, `c2c-input-source`). Proves that active asynchronous RPCs remain pending and uncorrupted while an independent input source streams continuous input events to the caller, and that neither stream corrupts, settles, or leaks into the other.

Scenario and observed behavior:
- Caller submits 8 outstanding asynchronous RPC calls to `c2c-input-provider` using `ostd::ipc::PendingCall::submit`.
- Provider captures all 8 operations and deliberately holds them without replying until signaled.
- Caller spawns `c2c-input-source`, which generates a continuous burst of 32 synthetic input event frames (`[tag=0 (Key), state=seq%2, scancode=seq, marker=0xAA]`) to the caller's mailbox.
- Caller drains all 32 input frames one-by-one from its mailbox, verifying:
  1. Exact sequence, sender identity, and frame payload integrity.
  2. Every one of the 8 in-flight RPC calls remains strictly pending (`try_take == Ok(None)`).
- After all 32 input events are drained, caller signals provider to release all 8 replies (`ostd::ipc::reply`).
- Caller drains all 8 RPC replies with `take_reply`, verifying:
  1. Exact sequence and 2-byte payload correlation (`[REQ_TAG, seq]`).
  2. Each token transitions to terminal `Reply` and rejects subsequent retries (`InvalidOperation`).
- Caller inspects its raw IPC mailbox with `sys_try_recv`: zero leaked RPC replies or misplaced frames (misplaced=0).
- Observed marker:
  `[local-lifecycle] CONCURRENT-INPUT=OK rpc_calls=8 input_events=32 rpc_settled=false rpc_drained=8 input_drained=32 misplaced=0`
  `[local-lifecycle] PASS`
  `[async-lifecycle] PASS`

Evidence ceiling:
Demonstrates non-interference and channel isolation between streaming input frames (mailbox) and asynchronous RPC operations (kernel operation table) in single-caller x86 QEMU.
