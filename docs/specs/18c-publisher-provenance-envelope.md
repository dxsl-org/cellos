# Publisher Provenance Envelope Contract

**Status:** Proposed — requires security-owner and independent-reviewer approval before implementation.

## Purpose and scope

This contract defines Claim A for Tier 1: a controlled CI/KMS publisher attests that a specific final ELF came from the reviewed source and build inputs. It supplements, but does not replace, the existing `__ViCell_sig` execution-content and manifest signature.

The current Tier 1 baseline is `rust-no-std` and remains **PARTIAL**. `rust-std` remains **PLANNED**. `ffi-posix` and Lua remain **PARTIAL trusted SAS profiles**; provenance does not make either a sandbox or a Tier-2 implementation.

No producer, kernel parser, production build profile, or admission path is introduced by this document. Production admission remains disabled until the external-floor and owner-record gates in Phase 03 are qualified and approved.

## Terms

- **Final ELF:** Exact bytes after `__ViCell_sig` is embedded and its current signature is re-verified.
- **Payload digest:** SHA-256 of the canonical current-signature payload: PT_LOAD segments ordered by `(p_offset, p_filesz, program-header index)`, followed by `__ViCell_manifest` bytes when present.
- **Envelope:** Canonically encoded, detached publisher statement about one Final ELF.
- **Publisher key ID:** SHA-256 of the public-key encoding used to verify the envelope signature.
- **Recipe digest:** SHA-256 of a canonical record of the allowed build command, inputs, and environment.

## Canonical envelope encoding, version 1

The envelope is a deterministic binary record. Integer values are unsigned big-endian. A byte string is encoded as its unsigned 32-bit length followed by bytes. A list is encoded as its unsigned 32-bit count followed by its elements. Every textual value is strict UTF-8 and is encoded as a byte string. A tuple concatenates its components in the listed order; every `sha256` value is exactly 32 bytes.

The exact top-level byte sequence is:

1. Domain separator: the 21 bytes `CELLOS-PROVENANCE-V1\0`, including its terminating NUL byte.
2. Schema version: unsigned 16-bit integer `1`.
3. The following fields, in this order, each encoded exactly once:
   1. `final_elf_sha256` — 32 bytes.
   2. `payload_sha256` — 32 bytes.
   3. `embedded_signature_sha256` — SHA-256 of the exact 64-byte `__ViCell_sig` value.
   4. `build_handoff` — `(ci_workload_identity, ci_receipt_sha256, unsigned_elf_sha256)`; the receipt is an authenticated CI build record and its output digest names the only artifact the signing gateway may consume.
   5. `publisher_key_id` — 32 bytes.
   6. `source_revision` — immutable VCS revision bytes.
   7. `source_is_dirty` — one byte; production value MUST be `0`.
   8. `tracked_inputs` — list of `(relative_path, sha256)` pairs, sorted by raw UTF-8 path bytes; paths MUST be relative, normalized, unique, and contain neither `.` nor `..` components.
   9. `f1_policy` — `(allowlist_sha256, checker_identity, result)` where `result` is one byte and production value MUST be `1`.
   10. `f5_policy` — `(rust_toolchain_toml_sha256, checker_identity, result)` where `result` is one byte and production value MUST be `1`.
   11. `dependency_lock_sha256` — 32 bytes when Cargo.lock applies; otherwise 32 zero bytes plus an explicit `dependency_lock_applicable=0` byte.
   12. `toolchain` — `(resolved_compiler_identity, target_triple, target_spec_sha256)`.
   13. `build_selection` — `(cargo_packages, cargo_profile, cargo_features, linker_identity, objcopy_identity)`; each list is sorted by raw UTF-8 bytes with no duplicates.
   14. `recipe_sha256` — 32 bytes.
   15. `environment_sha256` — SHA-256 of the sorted allowlisted `(name, value)` pairs. Omitted, secret, or unallowlisted environment values are not represented by a default.
   16. `build_invocation_id` — 16 opaque bytes generated by controlled CI.
   17. `issued_at_unix_seconds` — unsigned 64-bit integer.

No tags, optional fields, extensions, duplicate fields, trailing bytes, unknown versions, invalid UTF-8, unsorted lists, or non-normalized paths are valid in version 1. Producers and consumers MUST reject them rather than silently preserving or ignoring data.

## Required source and build binding

`tracked_inputs` MUST include every Cell crate root, all tracked Rust files under `cells/`, and `scripts/unsafe-allowlist.toml`. The F1 checker identity and result bind that exact checked set; the F5 checker identity and result bind the pinned toolchain file. `libs/*` is reviewed TCB and is explicitly outside the F1 scanned-input boundary; it MUST NOT be implied to have been scanned by this envelope.

The producer MUST bind the exact Cargo package set, release profile, feature set, target triple or target JSON digest, linker and objcopy identity, resolved compiler identity, dependency-lock digest, image recipe, and allowlisted environment. Any board or package feature selected by a build lane is part of `build_selection`.
The isolated CI builder MUST create an authenticated, immutable receipt after F1/F5 pass and before the artifact leaves its boundary. The receipt MUST bind its workload identity, `build_invocation_id`, all source/build fields in this envelope, and `unsigned_elf_sha256` for the exact unsigned output. The CI/KMS signing gateway MUST authenticate that receipt, fetch that digest from an immutable content-addressed build-output store, and reject raw file paths, caller-supplied byte streams, a receipt/output mismatch, an unauthorized workload identity, or an expired/reused receipt. It then embeds and re-verifies `__ViCell_sig` itself; no post-build caller may substitute the artifact.

The publisher signs the complete encoded envelope using Ed25519. The detached signature is exactly 64 bytes and the public key is selected only by the 32-byte `publisher_key_id`. The production publisher key is CI/KMS custody material. Reproducible development keys, `--unchecked-dev-signature`, arbitrary local key material, and direct low-level signer invocations MUST produce non-production artifacts.

## Producer sequence

1. Resolve and record the source, dependency, toolchain, target, recipe, and allowed environment inputs.
2. Run F1 and F5 on those inputs; reject failure before a build starts.
3. Build the native artifact in the isolated CI builder, hash its exact unsigned bytes, and issue the authenticated build receipt.
4. Have the CI/KMS signing gateway authenticate the receipt and fetch the matching unsigned output from the content-addressed store. It embeds the existing `__ViCell_sig` and re-verifies that signature.
5. Hash the exact resulting Final ELF, the canonical payload, and the embedded signature.
6. Encode the envelope with the receipt handoff, sign it in CI/KMS, and publish the ELF, envelope, and detached envelope signature as one install bundle.

The envelope is detached because embedding a statement that hashes Final ELF bytes would create a self-reference. A source check followed by signing an arbitrary supplied target path does not establish this binding and MUST be rejected by the production signing gateway.

## Consumer sequence and rejection rules

A future production consumer MUST:

1. Verify the existing `__ViCell_sig` over the canonical payload.
2. Obtain the exact loaded ELF bytes and recompute Final ELF, payload, and embedded-signature digests.
3. Strictly decode the version-1 envelope and verify its detached signature with the provisioned publisher anchor matching `publisher_key_id`.
4. Require every recomputed digest and every declared build identity to match the envelope and the approved production policy.
5. Only then pass the Final ELF digest to the separately owner-authorized, external-floor-pinned admission check.

Any missing envelope, bad signature, unknown key, unknown encoding, malformed field, mismatched digest, failed F1/F5 result, dirty production source, stale build identity, or post-sign mutation MUST reject Claim A. A valid current `__ViCell_sig` alone is insufficient for future production admission. Path labels and `SpawnFromMem` caller names have no authority and follow this same content-addressed check.

## Required evidence

The implementation test suite MUST cover canonicalization disagreement, field-order and trailing-byte rejection, malformed and unknown versions, final-ELF and payload-digest mismatch, wrong publisher key, missing envelope, stale source/dependency/toolchain/recipe data, unchecked development signatures, post-sign ELF mutation, raw-path/raw-byte signing requests, a mismatched or replayed build receipt, and a receipt whose output digest names different bytes. Evidence MUST show both path-backed and memory-backed spawn delivery reach the same decision.

Before a production feature can enable, the security owner and a reviewer independent of the author MUST approve this contract, its threat model, and the test evidence. Any change to the canonical encoding, publisher key policy, source boundary, toolchain binding, build recipe, or loader verification path invalidates that approval.
